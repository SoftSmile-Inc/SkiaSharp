# Спецификация: удалённая сборка нативных библиотек SkiaSharp

Как форк `SoftSmile-Inc/SkiaSharp` производит артефакты для Unity-проекта `vision` и как они туда
попадают. Документ описывает, что должно получиться; выбор между вариантами зафиксирован в
[ADR](../adr/). Терминология — в [CONTEXT.md](../../CONTEXT.md).

Статус: согласовано; реализовано в ветке `ci/native-build`, полный прогон зелёный. Путь релиза проверен черновиком
на тестовом теге (публикация не-черновиком и анонимное скачивание не проверены). После неудачной попытки приёмки
(`duplicate symbol` при линковке плеера) состав WebGL-слотов изменён
([ADR 0004](../adr/0004-webgl-harfbuzzsharp-binds-to-unity-harfbuzz.md)); бандл с новым составом в Unity ещё не
принят. В `main` не влито.

---

## 1. Задача

Сегодня библиотеки собираются на машине разработчика и копируются в `vision` руками. Какая
сборка породила лежащие там байты — не записано нигде; совпадает ли их версия с той, что бэкенд
тянет из NuGet, — тоже. Цель CI: сделать сборку воспроизводимой по тегу, а соответствие версий —
проверяемым автоматически.

Из форка собирается не всё. Stock-пакеты с nuget.org используются везде, где правка форка
соответствующий таргет не затрагивает.

## 2. Матрица артефактов

| Слот в `Assets/ExternalPlugins/` | Источник | Почему |
|---|---|---|
| `WebGL/libSkiaSharp.a` | форк-сборка | переименование символов freetype2/libjpeg-turbo/libpng |
| `WebGL/SkiaSharp.dll` | форк-сборка | `__Internal` в P/Invoke |
| `WebGL/HarfBuzzSharp.dll` | форк-сборка | `__Internal` в P/Invoke |
| `x86_64/libHarfBuzzSharp.so` | форк-сборка | `-Wl,-Bsymbolic-functions` против интерпозиции символов |
| `x86_64/libSkiaSharp.so` | stock | `SkiaSharp.NativeAssets.Linux.NoDependencies`, `runtimes/linux-x64/native/` |
| `x86_64/libSkiaSharp.dll` | stock | `SkiaSharp.NativeAssets.Win32`, `runtimes/win-x64/native/` |
| `x86_64/libHarfBuzzSharp.dll` | stock | `HarfBuzzSharp.NativeAssets.Win32`, `runtimes/win-x64/native/` |
| `MacOS/libSkiaSharp.dylib` | stock | `SkiaSharp.NativeAssets.macOS`, `runtimes/osx/native/` (universal) |
| `MacOS/libHarfBuzzSharp.dylib` | stock | `HarfBuzzSharp.NativeAssets.macOS`, `runtimes/osx/native/` (universal) |
| `SkiaSharp.dll`, `SkiaSharp.HarfBuzz.dll`, `HarfBuzzSharp.dll` (корень) | stock | обычные managed-сборки для всех платформ кроме WebGL |

**`WebGL/libHarfBuzzSharp.a` не поставляется.** В WebGL-плеере уже есть harfbuzz Unity, и
HarfBuzzSharp работает на нём; наша копия рядом с ним даёт сотни `duplicate symbol` при линковке
([ADR 0004](../adr/0004-webgl-harfbuzzsharp-binds-to-unity-harfbuzz.md)). Если файл лежит в
`vision`, его удаляют вместе с `.meta` (§7.2).

Не производится и не поддерживается: `linux-arm64`, `win-x86`, `win-arm64`, а также
`__Internal`-варианты `SkiaSharp.Skottie`, `SkiaSharp.SceneGraph`, `SkiaSharp.Resources` — их нет
в графе зависимостей Unity-приложения.

`.meta`-файлы слотов закоммичены в `vision` и содержат настройки платформ. CI их **не трогает**:
обновление бандла заменяет байты, GUID и настройки импорта сохраняются.

## 3. Джобы сборки

Все четыре независимы и выполняются параллельно. Конфигурация везде Release.

### 3.1. wasm

```bash
bash scripts/Docker/wasm/build-local.sh 3.1.39 \
  --wasmRenameThirdPartySymbols=true \
  --emscriptenFeatures=_wasmeh,st,simd
```

Команда фиксирована и изменению не подлежит. Она сама собирает образ `skiasharp-wasm:3.1.39`,
запускает в нём `dotnet cake --target=externals-wasm` и производит оба архива. В бандл идёт только
`libSkiaSharp.a`; `libHarfBuzzSharp.a` проверяется (§5.1, §5.2), но не поставляется (§2).

Результат ложится во внутренний layout:

```
output/native/wasm/libSkiaSharp.a/3.1.39/st,simd/libSkiaSharp.a
output/native/wasm/libHarfBuzzSharp.a/3.1.39/st,simd/libHarfBuzzSharp.a
```

Вложенность `<версия>/<модификаторы>/` — следствие того, что элементы набора фич, начинающиеся с
`_`, из пути выбрасываются, а остальные джойнятся через запятую. Это ожидаемое поведение,
менять его нельзя: тот же layout является входом для nuspec и `IncludeNativeAssets.*.targets`.

Набор фич `_wasmeh,st,simd` выведен из `ProjectSettings/ProjectSettings.asset` Unity-проекта:
`webGLThreadsSupport: 0` даёт `st`, `webWasm2023: 1` включает native WebAssembly exceptions и SIMD,
что соответствует `_wasmeh` и `simd`.

Образ `skiasharp-wasm:3.1.39` остаётся в локальном docker после сборки и используется джобой
проверок (§5.1).

### 3.2. linux

```bash
cd scripts/Docker/debian/amd64 && docker build --tag skiasharp-linux-x64 .
cd - && docker run --rm --volume "$(pwd)":/work skiasharp-linux-x64 /bin/bash -c \
  "dotnet tool restore && dotnet cake native/linux/build.cake --target=libHarfBuzzSharp --buildarch=x64"
```

Собирается только таргет `libHarfBuzzSharp` — это один амальгамированный `.cc`, минуты, а не
полная сборка Skia. Результат: `output/native/linux/x64/libHarfBuzzSharp.so` и версионированный
`libHarfBuzzSharp.so.<soname>`.

На чистом чекауте команда сама по себе не работает. Закреплённый `depot_tools` использует голый
декоратор `@functools.lru_cache`, который Python 3.7 из образа debian:10 не принимает, и
`ninja.py` падает на импорте. Патч `@functools.lru_cache()` в `native/linux/build.cake` живёт
только в задаче `libSkiaSharp`, которая здесь не выполняется; upstream этого не замечает, потому
что его цель по умолчанию сначала собирает `libSkiaSharp`. Поэтому перед сборкой workflow
применяет тот же патч к рабочей копии сабмодуля и проверяет, что голых декораторов не осталось.

### 3.3. managed `__Internal`

```bash
dotnet build binding/SkiaSharp/SkiaSharp.csproj -f netstandard2.1 -c Release \
  -p:SkiaSharpUnityWebGLInternal=true -o artifacts/unity-webgl
dotnet build binding/HarfBuzzSharp/HarfBuzzSharp.csproj -f netstandard2.1 -c Release \
  -p:SkiaSharpUnityWebGLInternal=true -o artifacts/unity-webgl
```

Проверено: обе сборки проходят в чистом `mcr.microsoft.com/dotnet/sdk:8.0` без единого файла в
`output/native/`, примерно за две секунды каждая. TFM именно `netstandard2.1`; `net8.0` не
подходит.

SDK — 8.0.x. `setup-dotnet` его только устанавливает, а выбирается самый новый SDK на раннере,
поэтому джоба дописывает версию в `global.json` рабочей копии (в репозитории версия SDK не
закреплена) и проверяет `dotnet --version`.

Свойство `SkiaSharpUnityWebGLInternal` передаётся именно как свойство, а не через
`-p:DefineConstants=...` — глобальное присвоение `DefineConstants` ломает собственные
`<DefineConstants>` проекта, включая тот, что выставляет `USE_LIBRARY_IMPORT`.

### 3.4. stock-нативы

Скачать с nuget.org восемь пакетов и взять по одному файлу из каждого — пять нативов:

| Пакет | Версия | Файл |
|---|---|---|
| `SkiaSharp.NativeAssets.Win32` | 3.119.2 | `runtimes/win-x64/native/libSkiaSharp.dll` |
| `HarfBuzzSharp.NativeAssets.Win32` | 8.3.1.3 | `runtimes/win-x64/native/libHarfBuzzSharp.dll` |
| `SkiaSharp.NativeAssets.macOS` | 3.119.2 | `runtimes/osx/native/libSkiaSharp.dylib` |
| `HarfBuzzSharp.NativeAssets.macOS` | 8.3.1.3 | `runtimes/osx/native/libHarfBuzzSharp.dylib` |
| `SkiaSharp.NativeAssets.Linux.NoDependencies` | 3.119.2 | `runtimes/linux-x64/native/libSkiaSharp.so` |

и три обычные managed-сборки для корневых слотов: `SkiaSharp`, `SkiaSharp.HarfBuzz`,
`HarfBuzzSharp` (`lib/netstandard2.1/`).

Версии не хардкодятся в workflow: версия каждого пакета читается из его собственной строки
`<пакет> nuget <версия>` в `scripts/VERSIONS.txt` собираемого ref, чтобы stock-часть бандла не
могла разойтись с той версией, из которой собрана форк-часть.

## 4. Версионирование и манифест

**Версия бандла** берётся из git-тега форка вида `v3.119.2-ss.N`: базовая часть совпадает с
upstream-релизом, суффикс наш. Сборка с ветки без тега даёт `3.119.2-dev.<короткий-sha>`.

**`versions.json`** кладётся в корень `Assets/ExternalPlugins/` вместе с файлами:

```json
{
  "bundle": "3.119.2-ss.1",
  "ref": "v3.119.2-ss.1",
  "commit": "3472e4041...",
  "ciCommit": "3472e4041...",
  "builtAt": "2026-09-16T12:00:00Z",
  "skiaSharp": "3.119.2",
  "harfBuzzSharp": "8.3.1.3",
  "emscripten": "3.1.39",
  "unity": "6000.3.8f1",
  "emscriptenFeatures": "_wasmeh,st,simd",
  "removedSlots": ["WebGL/libHarfBuzzSharp.a"],
  "files": [
    { "slot": "WebGL/libSkiaSharp.a", "source": "fork", "sha256": "..." },
    { "slot": "x86_64/libSkiaSharp.dll", "source": "nuget:SkiaSharp.NativeAssets.Win32/3.119.2", "sha256": "..." }
  ]
}
```

`commit` — собранный коммит: `prepare` разрешает целевой ref в SHA один раз, и все джобы собирают
именно его. `ciCommit` — коммит, из которого взяты workflow и скрипты CI (§8); при сборке по тегу
они совпадают, при ручном запуске на release-ветке могут различаться. `ref` — имя, по которому
запросили сборку (тег или ветка), только для чтения человеком. `removedSlots` — слоты, которых в
бандле больше нет и которые при переносе удаляются из `vision` вместе с `.meta` (§7.2).

Поля `skiaSharp` и `harfBuzzSharp` — две независимые версионные оси; именно на их смешении
возникает рассинхрон, поэтому они записываются раздельно. Поле `unity` фиксирует, под какую
версию редактора собран wasm (см. §7.3).

## 5. Проверки

### 5.1. Блокирующие публикацию

Выполняются в джобе сборки, сразу после неё, в том же образе. Ни одна не требует Unity.

**Переименование сработало.** На `libSkiaSharp.a`:

```bash
docker run --rm --volume "$(pwd)":/work skiasharp-wasm:3.1.39 \
  emnm --defined-only --extern-only \
  output/native/wasm/libSkiaSharp.a/3.1.39/st,simd/libSkiaSharp.a
```

- нет глобальных символов, начинающихся с `FT_`, `png_`, `jpeg_` без префикса `sksharp_`;
- символы `sksharp_*` присутствуют;
- символы `sk_*` присутствуют под исходными именами — собственный C API SkiaSharp затронут быть
  не должен.

Проверяются только префиксы `FT_`, `png_`, `jpeg_`. Сверка с полным списком переименованных имён
из сгенерированного `wasm_symbol_renames.h` — возможное усиление, пока не сделано.

Про `Cr_z_*` (zlib) проверок нет: zlib сознательно исключён из механизма, его вендоренный
Chromium-форк уже префиксует свои символы сам.

Проверки `libHarfBuzzSharp.a` ниже относятся к архиву, который не поставляется (§2). Они держат
механизм переименования в известном состоянии до этапа B
[ADR 0004](../adr/0004-webgl-harfbuzzsharp-binds-to-unity-harfbuzz.md), где проверка алиасов
сменится проверкой их отсутствия.

**Алиасинг harfbuzz сработал.** На `libHarfBuzzSharp.a`: каждое имя `hb_*`, которое
P/Invoke'ит managed-биндинг (список извлекается из `binding/HarfBuzzSharp/HarfBuzzApi.cs` и
`HarfBuzzApi.generated.cs` тем же способом, что и в `GetHarfBuzzManagedApiNames`), присутствует
в архиве под **исходным** именем. В плеере алиасы сейчас не участвуют (ADR 0004); проверка фиксирует
состояние механизма до этапа B. Кроме того, в архиве
есть символы `sksharp_hb_*`: без этого предыдущая проверка прошла бы и на архиве, где
переименование harfbuzz не сработало вовсе.

Первый же полный прогон этой проверкой нашёл реальный дефект: генератор `wasm_symbol_aliases.h`
объявлял алиасы без `extern "C"`, и в C++-единице трансляции все 314 алиасов экспортировались
mangled (`_Z14hb_blob_createv`), а не под именем, которое ищет P/Invoke. Тот же дефект — в архиве,
который использовался в Unity-проекте до CI. Исправлено в `native/wasm/build.cake`; при повторении
проверка сама сообщает, что у алиасов C++-линковка. Исправление сделало наш объект достижимым для
линкера и вскрыло конфликт с harfbuzz Unity — отсюда ADR 0004.

**`-Wl,-Bsymbolic-functions` применился.** На `libHarfBuzzSharp.so`: `readelf -r --wide` не
показывает ни одной релокации `JUMP_SLOT` на `hb_*`, при этом хотя бы одна `JUMP_SLOT` вообще
есть — иначе ноль был бы пустым проходом. Без флага таких записей десятки
(см. `documentation/linux-harfbuzz-symbol-interposition.md`).

**`__Internal` попал в managed-сборки.** В `SkiaSharp.dll` и `HarfBuzzSharp.dll` присутствует
строка `__Internal` и отсутствуют `libSkiaSharp` / `libHarfBuzzSharp`.

Все сообщения проверок, включая `FAIL`, попадают в summary прогона. При падении джобы wasm или
linux её выход (`output/native/...` и сгенерированные заголовки переименования) выгружается
отдельным артефактом на 7 дней, чтобы разбор не требовал пересборки.

### 5.2. Сторож незащищённых C++-символов

Считает в `libHarfBuzzSharp.a` глобальные определённые символы, начинающиеся с `_Z` (mangled
C++). Переименованные символы начинаются с `sksharp_`, поэтому все `_Z*` — незащищённые. Падает,
если число выросло относительно зафиксированной базовой линии.

Базовая линия хранится в `documentation/ci/harfbuzz-symbol-baseline.txt` (первое число в файле).
Пока файла нет, сторож только печатает измеренное значение и ничего не блокирует. Файл берётся из
коммита CI, а не из собираемого ref (§8). Базовая линия — **2194** (первый полный прогон
с C-линковкой алиасов; SkiaSharp 3.119.2, HarfBuzzSharp 8.3.1.3, emscripten 3.1.39,
`_wasmeh,st,simd`). До исправления алиасов было 2508: 314 mangled-алиасов тоже попадали в `_Z*`.
Не путать с числом 1027 — это другая
величина: количество имён, совпадающих одновременно в нашем архиве и в архиве Unity
`WebGLSupport_UnityPlayer.TextRenderingModule_Dynamic.a`.

Из 2194 ошибку линковки способны дать только 161 strong-определение; остальные 2033 — weak
(шаблоны, inline), они при совпадении молча сливаются. Против архива Unity 6000.3.8f1 strong-
пересечение — 125 имён. Пока архив не поставляется (§2), сторож — ориентир для этапа B, а не защита
плеера. Падает он и проверки §5.1 для `libHarfBuzzSharp.a` по-прежнему блокируют публикацию —
намеренно: сдвиг механизма замечается в момент, когда он произошёл, а не при начале этапа B.

Сторож ничего не чинит. Он превращает молчаливый риск в сигнал на нашей стороне при DEPS-бампе
harfbuzz, смене флагов или правке механизма. Исходное обоснование —
[ADR 0003](../adr/0003-harfbuzz-cpp-internals-residual-risk.md), заменённый
[ADR 0004](../adr/0004-webgl-harfbuzzsharp-binds-to-unity-harfbuzz.md).

### 5.3. Приёмка

Автоматической приёмки нет. Бандл считается пригодным после того, как на нём собран Web DFA,
задеплоен на dev и проверен человеком в браузере — рендер отшейпленного текста разными шрифтами.
Это решение разработчика: ни одна автоматическая проверка его в этом не убеждает.

Кандидат на приёмку — это тег `v<база>-ss.N` и его релиз, а не дев-сборка: артефакты прогонов
GitHub скачиваются только с токеном, а джоба переноса в `vision` ходит на GitHub анонимно (§7.2).
Не прошедший приёмку кандидат остаётся в истории релизов; следующий получает `N+1`, номер не
переиспользуется.

Отдельного пункта про генерацию PDF не нужно: по текущим требованиям PDF в WebGL не генерируется.
До правок форка такой возможности и не было — мешали как раз «ванильные» `libSkiaSharp` и
`libHarfBuzzSharp`. Соответственно, расхождение QuestPDF `[2022.12.0]` (компилировался против
SkiaSharp 2.88) с резолвящимся 3.119.2 остаётся вопросом бэкенда, а не плеера.

## 6. Публикация

Релизная сборка (по тегу) прикладывает бандл к GitHub Release этого тега. Бандл — один архив:
файлы, разложенные по именам слотов, плюс `versions.json`. Тег должен иметь вид
`v<база>-ss.<N>`, где `<база>` совпадает с версией SkiaSharp в `scripts/VERSIONS.txt`
помеченного коммита; иначе `prepare` отказывает за секунды. Опубликованный бандл не
перезаписывается: если у релиза уже есть архив, публикация падает — нужен новый `N`.

Публикацию выполняет отдельная джоба — единственная с правом записи; она не делает чекаут и не
исполняет кода из репозитория, только скачивает готовый архив и вызывает `gh release`.

Дев-сборка (ветка без тега) кладёт тот же архив в артефакты прогона, ретенция 14 дней, в Release
не попадает. Скачать его можно только с токеном GitHub, поэтому для `vision` он недоступен (§5.3).

Релизы хранятся бессрочно. В S3 не дублируются: бандл воспроизводим из тега, а вторая копия —
это второе место, где версия может разойтись.

## 7. Доставка в `vision`

### 7.1. Предварительное условие

**До первого прогона CI** отдельным MR в `vision` добавить в `.gitattributes`:

```
*.a filter=lfs diff=lfs merge=lfs -text
*.dylib filter=lfs diff=lfs merge=lfs -text
```

и перевести уже закоммиченные файлы через `git lfs migrate import --no-rewrite` (эта команда
упомянута комментарием в самом `.gitattributes`). Сейчас `libSkiaSharp.a` (15.1 МБ),
`libHarfBuzzSharp.a` (3.4 МБ) и `libSkiaSharp.dylib` (~15.8 МБ) лежат сырыми блобами. Записаны
они по одному разу, поэтому ущерба ещё нет — но каждое обновление бандла добавит в историю
`vision` ещё около 31 МБ навсегда (`libHarfBuzzSharp.a` из бандла убран, §2).

### 7.2. Перенос

Ручная джоба в пайплайне `vision` с параметром «версия бандла». Она скачивает архив с GitHub
Release, раскладывает файлы по слотам, пишет `versions.json`, коммитит в новую ветку и открывает
MR.

Слоты из поля `removedSlots` манифеста удаляются вместе со своими `.meta`, если они есть. Сейчас
там `WebGL/libHarfBuzzSharp.a`: он лежит в `vision` с ручной сборки, а в бандле его нет (§2).
Удалять «всё, чего нет в манифесте» нельзя — в тех же каталогах лежат чужие плагины. Пока джобы
переноса нет, файл удаляют руками в том же MR, который приносит первый бандл; то же написано в
описании релиза.

Направление доступа выбрано осознанно: GitLab ходит на GitHub, а не наоборот. Релизы публичного
репозитория читаются анонимно, поэтому ни один секрет не пересекает границу систем и в публичном
форке не появляется токена с правом записи в основной репозиторий. Обоснование —
[ADR 0002](../adr/0002-ci-home-for-public-fork.md).

### 7.3. Проверка согласованности

Джоба в пайплайне `vision`, блокирующая MR. Сверяет `versions.json` с двумя источниками:

1. `skiaSharp` и `harfBuzzSharp` — против `PackageReference` в csproj бэкенда
   (`Backend/SoftSmile.Vision.Fonts/SoftSmile.Vision.Fonts.csproj`);
2. `unity` — против `UNITY_VERSION` в `ci/unity-mono-gitlab-ci.yml`.

Вторая проверка ловит апгрейд Unity. Версия emscripten следует из версии Unity (6000.3.8f1 несёт
3.1.39), а лежащий в слотах `.a` — полуфабрикат, который дособирает сама Unity своим тулчейном.

После [ADR 0004](../adr/0004-webgl-harfbuzzsharp-binds-to-unity-harfbuzz.md) у неё появился и
известный режим слома: HarfBuzzSharp в WebGL работает на harfbuzz самой Unity, и апгрейд может
поменять его версию или состав. Сама джоба пока не реализована.

В остальном это **подстраховка, а не защита от известного слома**. Расхождение в пределах минорной версии на
практике безвредно: разработчик собирал архив emscripten 3.1.34 и линковал его той же Unity
6000.3.8f1 с её 3.1.39 — всё работало. Проверка нужна на случай крупного скачка при апгрейде
Unity, когда разойтись может уже не патч-версия; ценность её в том, что сообщение появится в том
самом MR, который поднимает версию Unity, а не через три недели в виде необъяснимого поведения.
Стоит она одного сравнения строк в джобе, которая и так есть, поэтому оставлена несмотря на
низкую вероятность срабатывания.

Проверку нельзя ставить в джобу `build AWS Web DFA`: на merge request она объявлена как
`when: manual` с `allow_failure: true`, то есть гейтом быть не может.

## 8. Триггеры

- **`workflow_dispatch`** с обязательным параметром `ref` (ветка или тег) и необязательными
  `emscripten_version`, `emscripten_features`, `unity_version`. Параметр `ref` обязателен потому,
  что новые версии SkiaSharp приезжают черри-пиком наших коммитов на новую release-ветку —
  фиксированной ветки для сборки не существует. Принимается только имя ветки или тега этого
  репозитория: голые SHA и `refs/pull/*` отвергаются. Ручной запуск никогда не публикует релиз.
- **push тега `v*-ss.*`** — релизная сборка с публикацией.
- Push в `release/*` без тега не собирается.
- Триггера `pull_request` нет и быть не должно.

Кнопка ручного запуска в UI появляется, только когда workflow лежит в ветке по умолчанию
(`main` форка — зеркало upstream). Без этого ручной запуск доступен через
`gh workflow run native-build.yml --ref <ветка с workflow> -f ref=<целевой ref>`, если workflow
хотя бы раз запускался.

### 8.1. Откуда берутся код и инструменты CI

В прогоне участвуют два коммита. **Целевой ref** `prepare` разрешает в один SHA, и все джобы
собирают именно его: сдвиг ветки во время многочасовой сборки не смешивает в бандле разные
коммиты. **Коммит CI** — тот, из которого взят сам workflow (`github.sha`): при ручном запуске это
голова ветки, указанной в `--ref`, при push тега — помеченный коммит.

Скрипты `.github/scripts/` и файл базовой линии `documentation/ci/` всегда берутся из коммита CI
(sparse checkout в `.ci/`), а сборочные входы — `scripts/VERSIONS.txt`, биндинги, cake — из
целевого ref. Поэтому release-ветке не нужно нести в себе CI: чтобы собрать её, достаточно
запустить workflow с ветки, где он есть. Тег — исключение: push тега запускает workflow из
помеченного коммита, так что релизный тег ставится на коммит, содержащий
`.github/workflows/native-build.yml`.

### 8.2. Защита публичного форка

Несущий контроль — **политики Actions** репозитория плюс **список разрешённых action**:

- upstream-workflow (все файлы `.github/workflows/`, кроме `native-build.yml`) можно запустить
  только вручную, то есть только пользователю с правом записи;
- `native-build.yml` принимает только `push` и `workflow_dispatch`;
- разрешены только четыре action, которые использует workflow.

Политики ограничивают события по пути workflow-файла и действуют на всех ветках, включая файлы,
которые ещё не зарегистрированы или появятся после синхронизации с upstream. Это важно, потому что
в `main` форка лежат upstream-workflow с `pull_request_target`, `issue_comment` и расписаниями.

Проверено на практике: push тега зарегистрировал upstream-workflow с триггером `push: paths:` (к тегам
path-фильтры не применяются) и создал для него прогон; политика отклонила его до старта джобов
(`startup_failure`). После первого push тега такие workflow дополнительно отключаются поштучно.

Остальное — дополнительные слои, на которые защита не опирается:

- «Require approval for all external contributors» не действует на `pull_request_target` и
  `issue_comment`, а PR из форка может принести собственный workflow — поэтому это не защита по
  устройству;
- зарегистрированные upstream-workflow отключаются поштучно, но отключить можно только уже
  зарегистрированный файл;
- `GITHUB_TOKEN` по умолчанию только на чтение; право записи объявлено явно у одной джобы
  публикации.

## 9. Раннер

Сборка идёт на **GitHub-hosted `ubuntu-latest`**. Для публичного репозитория это 4 ядра, 16 ГБ
RAM и гарантированные 14 ГБ SSD; минуты бесплатны и не лимитированы, лимит джобы — 6 часов.

`build-local.sh` работает там дословно: шаги `run:` исполняются на хосте, docker установлен,
`$(pwd)` — настоящий путь хоста. Это существенно: под docker-executor с проброшенным сокетом
(конфигурация сборочного флота GitLab) `docker run -v $(pwd):/work` смонтировал бы
несуществующий путь и сборка стартовала бы в пустом каталоге.

**Измерено** (2026-09-27, три холодных прогона wasm-джобы, образ ubuntu-24.04; тогда джоба ещё начиналась
с шага освобождения диска):

| | |
|---|---|
| сборка (`build-local.sh`, включая сборку образа) | 428, 501 и 700 с — 7–12 минут |
| wasm-джоба целиком | 9–15 минут, из них ~2 минуты — шаг освобождения диска |
| корневой диск раннера | 145 ГБ; свободно 86 ГБ до очистки, 114 ГБ после |
| пик занятого места во время сборки | 36,0 ГБ при 31,0 ГБ после очистки — сборка добавляет ~5 ГБ (повторяемо) |
| после сборки | `externals/skia` 2,2 ГБ, `output/` 19 МБ |

Прежняя оценка «12–18 ГБ на прогон» не подтвердилась: прирост около 5 ГБ плюс чекаут с сабмодулями
укладываются даже в гарантированные 14 ГБ. Поэтому шага освобождения диска в джобе больше нет — он
стоил около двух минут на прогон. Если диска когда-нибудь не хватит, его можно вернуть: снос
преустановленных Android SDK, .NET, GHC, CodeQL, PowerShell и Swift освобождал около 28 ГБ.

Требования по изоляции публичного форка выполняются по устройству: раннер эфемерный, вне нашей
VPC, доступа к боевым сервисам не имеет. Секретов у сборки нет вообще — `GITHUB_TOKEN` нужен
только для создания релиза.

**Каждая джоба стартует на чистой виртуальной машине**, поэтому чистка результатов предыдущей
сборки не нужна. Это не мелочь: `externals/skia/out/wasm-symgen` между прогонами не чистится
самим билдом (известное ограничение механизма), и на машине с сохраняемым состоянием перед
каждым прогоном пришлось бы делать

```bash
rm -rf externals/skia/out/wasm-symgen externals/skia/out/wasm
```

При переезде на self-hosted этот шаг становится обязательным — либо раннер должен быть
эфемерным, что и рекомендуется ниже.

**Порог переезда на self-hosted.** Переезжаем, если выполнено любое из:

- не помещаемся в диск даже с возвращённым шагом освобождения диска;
- холодная сборка стабильно дольше 90 минут.

По замерам выше ни одно условие не выполняется с большим запасом (максимум 12 минут против 90; ~5 ГБ
прироста при 86 ГБ свободных без всякой очистки), поэтому **остаёмся на GitHub-hosted**.

Переезд — это смена `runs-on:` плюс провижининг EC2 (c7a.4xlarge, 200+ ГБ gp3, executor shell,
агент `--ephemeral`, отдельная security group с исходящим 443 через NAT). Остальная часть
спецификации от этого не зависит.

## 10. Открытые вопросы

1. **Владельцы.** Настройки Actions форка (§8.2) выставлены администратором организации. Кто
   отвечает за них дальше и кто апрувит изменения `.gitlab-ci.yml` в `vision` — не установлено.

2. **Приёмка бандла без `WebGL/libHarfBuzzSharp.a`** (§2, ADR 0004) — нужна сборка Web DFA и
   проверка в браузере. Заодно выяснить, ссылается ли IL2CPP на восемь функций `hb_buffer_[de]serialize*`,
   которых нет у harfbuzz Unity.

Закрыто по ходу согласования: генерация PDF в WebGL-плеере не выполняется (§5.3); команды сборки
в §3 подтверждены разработчиком. Закрыто первым полным прогоном: базовая линия сторожа (§5.2) и
время и пиковый диск холодной сборки (§9). Закрыто разбором на архиве Unity: как разрешались `hb_*`
в плеере до исправления алиасов — в harfbuzz Unity (ADR 0004).
