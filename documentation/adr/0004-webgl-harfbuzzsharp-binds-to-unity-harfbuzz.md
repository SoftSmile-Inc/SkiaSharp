# В WebGL HarfBuzzSharp работает на harfbuzz Unity, свой не поставляем

Статус: accepted (2026-10-01). Заменяет [ADR 0003](0003-harfbuzz-cpp-internals-residual-risk.md).

В бандле для WebGL нет `libHarfBuzzSharp.a`. `HarfBuzzSharp.dll` в варианте `__Internal` вызывает
`hb_*`, которые предоставляет копия harfbuzz, уже входящая в WebGL-плеер Unity. Архив по-прежнему
собирается (команда wasm-сборки неизменна) и проверяется в CI, но не поставляется. Это первый этап;
второй — полная изоляция нашей копии — описан ниже и пока не принят.

## Контекст

В WebGL-плеере Unity 6000.3.8f1 есть собственный harfbuzz Unity — по строке версии в архиве это
8.0.1. Он живёт в модуле TextRendering, и его подтягивает модуль TextCoreTextEngine (вызывает
`hb_shape`, `hb_buffer_*`, `hb_ft_*`), от которого зависят UI Toolkit и IMGUI. Модули формально
вырезаемые, но пока проект использует IMGUI или UI Toolkit — как `vision` сейчас, — harfbuzz Unity в
плеере есть. Наш harfbuzz — 8.3.1.

Механизм форка (переименование, `-fvisibility=hidden`, обратные алиасы, см.
`documentation/wasm-symbol-renaming.md`) должен был позволить нашей копии жить рядом с копией Unity.
Проверка на настоящем архиве Unity (`TextRenderingModule_Dynamic.a`) и его же `wasm-ld` (LLD 17)
показала, что не может:

- Статическая линковка решает конфликт по привязке символа, а не по видимости. Два strong-определения
  одного имени — `duplicate symbol` при любой visibility, для C и для C++. `-fvisibility=hidden` не
  защищает ничего; C-интерналы harfbuzz защищены только текстовым переименованием. Weak-определения
  (шаблоны, inline) не конфликтуют, а молча сливаются: strong всегда побеждает weak, из двух weak
  побеждает загруженное первым.
- В нашем архиве 161 strong mangled C++-символ; 125 из них определяет и Unity. Из 319 имён `hb_*`,
  которые P/Invoke'ит биндинг, 311 Unity определяет сам.
- Как только наш объект попадает в линковку, получается 436 `duplicate symbol`. Ровно это произошло
  после того, как алиасы `hb_*` стали экспортироваться с C-линковкой.

До этого исправления алиасы экспортировались под C++-mangled именами, на наш объект ничего не
ссылалось, и `wasm-ld` его просто не загружал. Все вызовы HarfBuzzSharp разрешались в harfbuzz Unity
— это и была конфигурация, принятая в браузере как рабочая. Объяснение ADR 0003 («ветку AAT
выбрасывает DCE») неверно: дубликаты проверяются при загрузке члена архива, до `--gc-sections`.

Plain-алиасы `hb_*` в нашем архиве опасны при любом раскладе: strong-алиасы дают `duplicate symbol`,
а weak-алиасы молча перехватили бы часть вызовов — и HarfBuzzSharp, и самого TextCore, — смешав в
одном плеере объекты двух разных копий.

## Решение

Этап A: не поставлять `libHarfBuzzSharp.a` для WebGL и оставить HarfBuzzSharp на harfbuzz Unity.
В части harfbuzz это та же конфигурация, что работала до CI, без конфликтов при любом порядке
линковки. Поставляемый `libSkiaSharp.a` проверен против всех wasm-модулей Unity 6000.3.8f1 и
системных библиотек emscripten: strong-пересечений нет.

## Последствия

- HarfBuzzSharp 8.3.1.3 работает поверх harfbuzz Unity 8.0.1, и в плеере это один экземпляр
  harfbuzz, общий с движком.
- Восьми функций, которые P/Invoke'ит биндинг, у Unity нет: `hb_buffer_serialize`,
  `hb_buffer_serialize_glyphs`, `hb_buffer_serialize_unicode`,
  `hb_buffer_serialize_format_from_string`, `hb_buffer_serialize_format_to_string`,
  `hb_buffer_serialize_list_formats`, `hb_buffer_deserialize_glyphs`,
  `hb_buffer_deserialize_unicode`. В плеере их вызвать нельзя — так было и раньше.
- Связь с внутренностями Unity: апгрейд Unity может поменять версию или состав её harfbuzz, а
  вырезание модуля TextRendering оставит P/Invoke без определений. Апгрейд будет ловить проверка
  согласованности (спецификация, §7.3); пока эта джоба не реализована — ручная проверка при апгрейде.
  После апгрейда нужна повторная приёмка.
- `WebGL/libHarfBuzzSharp.a` перечислен в `removedSlots` манифеста: при переносе бандла его удаляют
  из `vision` вместе с `.meta` (спецификация, §7.2). Без этого прежний файл останется на месте, и
  все конфликты вернутся.
- ADR 0003 заменён: его риск снят для поставляемого бандла, а его описание механизма неверно.
  Сторож из спецификации §5.2 продолжает считать `_Z*` в непоставляемом архиве — как ориентир для
  этапа B.

## Этап B (не принят)

Полная изоляция нашей копии, чтобы HarfBuzzSharp работал на своём harfbuzz 8.3.1 рядом с Unity:

- в варианте `__Internal` биндинг вызывает переименованные имена: `EntryPoint = "sksharp_hb_…"`
  через генератор биндингов. IL2CPP Unity 6000.3.8f1 учитывает `EntryPoint` для `__Internal` —
  проверено его же конвертером;
- top-level C++-идентификаторы harfbuzz (`OT`, `AAT`, `hb_buffer_t`, …) переименовываются
  генерируемыми макросами по тому же принципу, что и C-имена; `::std` не затрагивается, поэтому
  проблема `std::hash` из ADR 0003 не возникает;
- пять функций, которые harfbuzz сам затеняет макросами (`hb_color_get_*`,
  `hb_glyph_info_get_glyph_flags`), получают `sksharp_`-имена;
- plain-алиасы `hb_*` не генерируются.

Прототип против настоящего архива Unity: 0 общих имён, 0 `duplicate symbol` при любом порядке
линковки. Реальной сборкой emsdk и в плеере не проверен; размер wasm вырастет на вторую копию
harfbuzz.

## Условия пересмотра

- Нужна одна из восьми отсутствующих у Unity функций или версия harfbuzz новее, чем у Unity.
- Апгрейд Unity убрал или заметно поменял её harfbuzz, или модуль TextRendering вырезан из плеера.
- Готов этап B.
