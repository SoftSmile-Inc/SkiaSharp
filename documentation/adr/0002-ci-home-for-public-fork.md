# CI живёт в GitHub Actions, доступ направлен из GitLab в GitHub

Статус: accepted (2026-09-16)

Сборка идёт в GitHub Actions на GitHub-hosted раннерах. Перенос бандла в `vision` инициируется
со стороны GitLab, а не со стороны GitHub. Никакой секрет не пересекает границу двух систем.

## Контекст

Исходники форка лежат на GitHub (`SoftSmile-Inc/SkiaSharp`, публичный репозиторий). Потребитель
артефактов, приёмка и проверка версий — в GitLab (`softsmile_group/vision`). То есть три из
четырёх точек соприкосновения находятся в GitLab, и перенос сборки туда выглядел бы логичным.

## Почему GitHub Actions

Сборка в GitLab потребовала бы зеркалирования форка: pull mirroring — это GitLab Premium, либо
самописный пуш с GitHub. Требование «CI собирает произвольную ветку, задаваемую параметром»
означает, что зеркалить надо все ветки, а не одну. Цена альтернативы — один токен с записью в
`vision`, и её удалось свести к нулю (см. ниже).

Отдельно: `scripts/Docker/wasm/build-local.sh` менять нельзя, а он делает
`docker run -v $(pwd):/work`. Это требует исполнителя, у которого рабочая директория джобы —
настоящий путь на хосте. Существующий сборочный флот GitLab использует docker-executor с
проброшенным сокетом хоста: `$(pwd)` внутри джобы это `/builds/...`, которого на хосте нет,
демон молча создал бы пустой каталог и сборка стартовала бы в пустом `/work`. То есть GitLab
потребовал бы ещё и нового раннера с shell-executor.

## Почему GitHub-hosted, а не свой раннер

Первоначально предполагался self-hosted раннер: оценка сборки Skia была 40–90 минут, а
GitHub-hosted даёт 4 ядра против 16 у c7a.4xlarge. Разработчик сообщил, что сборка занимает
минуты, а не часы, и главный аргумент исчез.

Для публичного репозитория стандартные GitHub-hosted раннеры бесплатны, минуты не лимитированы.
Диска (14 ГБ) не хватает — один прогон занимает 12–18 ГБ — но штатный шаг очистки образа
освобождает ещё 25–45 ГБ.

Существеннее стоимости то, что GitHub-hosted **выполняет требования безопасности по
устройству**: раннер эфемерный, живёт вне нашей VPC, доступа к боевым сервисам не имеет в
принципе. Self-hosted потребовал бы провижининга машины, systemd-сервиса `--ephemeral` и
отдельной security group — и всё это ради сборки раз в несколько недель.

Порог обратного перехода записан в [спецификации](../ci/native-build-spec.md#9-раннер) как
измеримое условие, а не как план.

## Почему доступ направлен из GitLab в GitHub

Бандл коммитится в `vision`, значит кто-то должен туда писать. Два варианта были:

- GitHub Actions пушит ветку в `vision` и открывает MR — требует токена с `write_repository`
  в secrets **публичного** репозитория, куда посторонние открывают PR;
- ручная джоба в пайплайне `vision` скачивает релиз с GitHub и открывает MR — релизы публичного
  репозитория читаются анонимно, токен не нужен вообще.

Выбран второй. Публичный форк — это место, где чужой код потенциально исполняется; хранить там
ключ от основного репозитория не следует, даже при выключенном триггере `pull_request`. Кроме
того, джоба живёт в том же репозитории, который она меняет, и её апрув нужен один раз.

## Последствия

- У сборки нет секретов: `GITHUB_TOKEN` нужен только для создания релиза.
- Триггера `pull_request` нет. «Require approval for all external contributors» в настройках
  Actions остаётся как защита в глубину, а не как несущий контроль.
- Перенос бандла требует нажатия кнопки в GitLab — сознательно, потому что обновление версии
  SkiaSharp в Unity-проекте должно проходить через ревью.
