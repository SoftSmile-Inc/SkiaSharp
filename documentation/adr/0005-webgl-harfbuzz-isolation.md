# Свой harfbuzz в WebGL: полная изоляция от harfbuzz Unity

Статус: proposed (2026-10-02) — реализовано в ветке `ci/native-build` (с коммита `3b98b84a8` CI собирает
бандлы по этому ADR), ждёт приёмки в Unity. После приёмки заменяет
[ADR 0004](0004-webgl-harfbuzzsharp-binds-to-unity-harfbuzz.md); до неё в `vision` действует ADR 0004, а
бандлы по этому ADR кладутся в `vision` только для приёмки.

В WebGL-плеере HarfBuzzSharp работает на нашем harfbuzz 8.3.1, а не на копии Unity. Наш
`libHarfBuzzSharp.a` не определяет ни одного имени, которое использует harfbuzz: всё переименовано
с префиксом `sksharp_`, а `HarfBuzzSharp.dll` в варианте `__Internal` вызывает переименованные
функции напрямую. Две копии harfbuzz живут в одном плеере, не касаясь друг друга.

## Контекст

[ADR 0004](0004-webgl-harfbuzzsharp-binds-to-unity-harfbuzz.md) разобрал, почему прежний механизм
не работал: в статической линковке два strong-определения конфликтуют при любой видимости, а
weak-определения молча сливаются. Наш объект конфликтовал с harfbuzz Unity по 125 C++-символам и
311 plain-именам `hb_*`. Этап A убрал наш архив из бандла, и HarfBuzzSharp стал работать на harfbuzz
Unity 8.0.1 — так, как он фактически работал и до CI. У этого есть цена: восьми функций, которые вызывает биндинг, у Unity нет, а поведение
зависит от версии и состава harfbuzz внутри Unity.

## Решение

Переименовать в нашем harfbuzz всё и не экспортировать ни одного исходного имени.

- **C API и прочие plain-имена** — как и раньше, сгенерированным `#define hb_x sksharp_hb_x` по
  символам discovery-сборки.
- **Функции, которые harfbuzz сам затеняет макросом** (`hb_color_get_*`,
  `hb_glyph_info_get_glyph_flags`) — `#pragma redefine_extname hb_x sksharp_hb_x`. Pragma меняет
  только имя символа и не трогает токены, поэтому идиома `(hb_x) (...)` в определении больше не
  мешает.
- **C++-символы** — `#define` для внешнего имени каждого mangled-символа discovery-сборки:
  пространства имён (`OT`, `AAT`, `CFF`, `graph`), глобальные классы и функции (`hb_buffer_t`,
  `hb_serialize_context_t`, `hb_aat_layout_compile_map`…) — 126 имён на 2194 mangled-символа. Переименование внешнего имени меняет и всё, что в нём
  вложено, в том числе weak-шаблоны. `::std` не трогается, поэтому проблема со специализацией
  `std::hash`, из-за которой в ADR 0003 отвергли обёртку в пространство имён, не возникает.
- **Алиасов нет.** Ни одного plain `hb_*` в архиве.
- **Managed.** Генератор биндингов получил опцию `entryPointPrefix`: в `HarfBuzzApi.generated.cs`
  у каждого P/Invoke `EntryPoint = HARFBUZZ_ENTRY_POINT_PREFIX + "hb_x"`. Константа равна
  `"sksharp_"` при MSBuild-свойстве `SkiaSharpHarfBuzzRenamedSymbols=true` — отдельном от
  `SkiaSharpUnityWebGLInternal`, потому что это две разные вещи: имя модуля и пара с переименованным
  архивом. Для варианта Unity WebGL свойство включено по умолчанию, во всех остальных вариантах
  константа `""`, и их поведение не меняется. IL2CPP Unity 6000.3.8f1 учитывает `EntryPoint` для
  `__Internal`.

Всё генерируется из той же discovery-сборки, что и раньше, в той же команде сборки; правок в
вендоренных исходниках harfbuzz нет.

## Как это проверяется

В CI (спецификация, §5.1): каждое имя, которое вызывает биндинг, определено как `sksharp_hb_*`; нет
ни одного plain `hb_*`; каждый определённый глобальный символ архива содержит `sksharp_`; архив не
ссылается на чужие harfbuzz-имена; в `HarfBuzzSharp.dll` для WebGL есть все 319 точек входа
`sksharp_hb_*`. Генератор падает, если не может разобрать mangled-имя или если для вызываемой
биндингом функции не будет переименованного определения.

Вне CI, на архивах первой сборки (2026-10-02):

- Линковка нашего архива вместе с настоящим архивом harfbuzz Unity 6000.3.8f1 — `wasm-ld` LLD 14 и
  собственным LLD 17 Unity, оба порядка, с `--gc-sections` и без: 0 `duplicate symbol` в 64 из 64
  моделей, обе копии harfbuzz загружены. `hb_shape` разрешается в harfbuzz Unity, `sksharp_hb_shape` —
  в наш. Общих определённых имён с любым из 128 wasm-модулей Unity — 0. Контроль: архив прежнего
  механизма в тех же моделях даёт ровно 436 ошибок.
- Конвертер IL2CPP Unity на `HarfBuzzSharp.dll` из бандла генерирует 319 прямых вызовов
  `sksharp_hb_*` и ни одного plain `hb_*`.
- Генератор биндингов с новой опцией даёт `HarfBuzzApi.generated.cs` байт в байт, без опции —
  прежний файл.

## Последствия

- В WebGL работают все 319 функций биндинга, включая `hb_buffer_serialize*`, и именно той версии
  harfbuzz, под которую написан HarfBuzzSharp 8.3.1.3.
- Поведение не зависит от того, есть ли в плеере harfbuzz Unity, какой он версии и в каком порядке
  линкер видит архивы.
- В wasm две копии harfbuzz; на сколько вырастет размер, покажет первая сборка в Unity.
- Набор переименований зависит от сборки и пересчитывается при каждой; изменения harfbuzz,
  которые генератор не поймёт, роняют сборку, а пропущенный символ ловит проверка CI.
- Вариант `__Internal` HarfBuzzSharp совместим только с этим архивом: со стоковым или старым
  `libHarfBuzzSharp.a` он не слинкуется. Обратное тише: прежняя `HarfBuzzSharp.dll` с новым архивом
  линкуется и молча остаётся на harfbuzz Unity. Оба слота переносятся вместе.
- С `--wasmRenameThirdPartySymbols=true` архив не экспортирует ни одного имени `hb_*` и подходит
  только HarfBuzzSharp, собранному с `SkiaSharpHarfBuzzRenamedSymbols=true` — по умолчанию это
  вариант для Unity WebGL, но свойство можно включить и для другого потребителя переименованного
  архива. Потребителям обычной wasm-сборки (например, статической линковке .NET WebAssembly) нужен
  архив без этого флага.
- Продуктовые правки этого ADR входят в набор коммитов, который черри-пикается на release-ветку;
  проверки CI без них падают.
- Сгенерированные идентификаторы вида `sksharp__glyf_…` с двойным подчёркиванием формально
  зарезервированы в C++; на практике это ни на что не влияет, так же было и у C-имён.

## Условия пересмотра

- Приёмка в Unity не прошла (конфликт, ошибка линковки, разница в рендере).
- Размер wasm вырос неприемлемо — тогда вернуться к ADR 0004.
- Обновление harfbuzz, которое ломает генерацию переименований.
