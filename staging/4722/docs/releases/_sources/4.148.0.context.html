Restore pulls 0.6.0 from the dotnet-public mirror; no nuget.config change ships.

      SKCanvas.DrawText(text, ..., SKFont, SKPaint) (the two overloads without an explicit SKTextAlign) are corrected from error back to warning. They were not obsolete in the last shipped stable (v3.119.x) — they were marked error during v4 development, skipping the deprecation-warning cycle. Per the deprecate-then- error policy a newly-deprecated API must first ship as a warning, so they ship as a warning in v4 and can be promoted to error in a later release.

      SKMetalView (Apple) is updated to call the GRBackendRenderTarget ctor without sampleCount, since the sampleCount overload is now an error.

      Fix SKPixmap/SKBitmap GetPixelSpan to use RowBytes for stride (#4148)

      Fixes: https://github.com/mono/SkiaSharp/issues/4137

      SKPixmap.GetPixelSpan(x, y) and SKBitmap.GetPixelSpan(x, y) computed both the span length and the (x, y) offset from Width * BytesPerPixel instead of the pixmap's actual RowBytes. For a subset created via ExtractSubset, the real stride is larger than Width * BytesPerPixel because the subset shares the parent's buffer, so the returned span was too short to cover the subset and the (x, y) offset landed on the wrong row. A 2x2 SKColor subset of a 4x4 RGBA8888 bitmap returned a span of length 4 instead of 6, and row 1 pointed at parent-row pixels.

      Compute both quantities from the actual stride:

      • length = (Height - 1) * RowBytes + Width * BytesPerPixel, which reaches the last valid pixel of the bottom row without reading the trailing row padding past the end of the (possibly shared) buffer.
      • offset = y * RowBytes + x * BytesPerPixel.

      For non-subset pixmaps RowBytes == Width * BytesPerPixel, so behaviour is unchanged. The offset is shared through a stride-aware SKImageInfo.GetPixelBytesOffset(x, y, rowBytes) helper, and the typed overload computes its length in element units (rowBytes / sizeof(T)) to avoid a byte-to-element division.

      Hardening surfaced during review:

      • out-of-range (x, y) throws ArgumentOutOfRangeException.
      • empty pixmaps/bitmaps and Unknown color types (BytesPerPixel <= 0) return an empty span before coordinate validation, preserving the prior behaviour.
      • the typed overload throws when a multi-row stride is not evenly divisible by sizeof(T); single-row (Height == 1) pixmaps are exempt since stride divisibility is irrelevant there.
      • all length/offset arithmetic is checked, including the (int) length cast in the no-argument SKBitmap.GetPixelSpan().

      The unused parameterless GetPixelBytesOffset overload (no production callers) was removed. No public signatures changed; this is a behaviour-only fix.

      Tests in SKPixmapTest and SKBitmapTest add the issue repro plus a GetPixelSpanReturnsExactSubsetPixels theory (in both classes) that builds an 8x6 Bgra8888 parent encoding each pixel's coordinates, extracts subsets at several origins -- (0,0), an interior non-square rect, the top and left edges at non-zero offsets, and the bottom-right corner -- and asserts every subset pixel against both the span and the independent GetPixelColor/GetPixel oracle, with each case requiring RowBytes > Width * BytesPerPixel. Further cases cover single-row, empty, Unknown, and a high-bit-shift (F32) color type, and the shared offset helper.

      Move native-compat gate from [ModuleInitializer] to SkiaApi cctor (#4133)

      Context: https://github.com/mono/SkiaSharp/pull/4080

      The singleton rework in #4080 removed the SKObject static constructor that used to trigger SkiaSharpVersion.CheckNativeLibraryCompatible, and re-added the check as a [ModuleInitializer]. A module initializer runs at assembly load — before any user code — which forces an eager P/Invoke into libSkiaSharp before a consumer can configure native-library loading (registering a DllImportResolver / NativeLibrary.SetDllImportResolver, or adjusting the search path). That regressed the "set up the native binary first, then use Skia later" pattern.

      Move the gate into SkiaApi's static constructor and delete SkiaSharpModuleInitializer.cs. SkiaApi is the single internal type through which every P/Invoke into libSkiaSharp flows, so an explicit static constructor (which strips the type's beforefieldinit flag) makes the CLR guarantee the check runs before the first sk_* call — on every interop configuration (USE_DELEGATES, USE_LIBRARY_IMPORT, direct DllImport) and every platform — without running at assembly load. This recovers the friendly supported-version-range message for all consumers, including code that only touches SKBitmap, SKCanvas, SKMatrix, or SKGraphics.

      Why it's safe:

      • Re-entrancy: CheckNativeLibraryCompatible reaches native via SkiaApi.sk_version_get_milestone / sk_version_get_increment while the cctor is still running. The CLR's same-thread type-initializer rule returns the in-progress SkiaApi type without re-running the body, and the only static state the version path reads (the USE_DELEGATES Lazy handle and its delegate cache) is a field initializer, which runs before the cctor body.
      • No #3817 regression: the cctor body touches only SkiaApi/LibraryLoader, never an SKObject, so it cannot reintroduce the static-initializer cycle.
      • Negligible cost: losing beforefieldinit adds a type-init readiness check that is masked by the P/Invoke transition itself (~0.35% on CoreCLR, statistically zero on Mono/net48).

      Builds clean on net48, net9.0, and netstandard2.0; version, singleton-init, and colorspace tests pass (35/35).

      Fix SKPixmap.GetPixelSpan(x, y) row stride offset (#4128)

      Fixes: https://github.com/mono/SkiaSharp/issues/4111

      The typed-access branch of GetPixelSpan<T>(int x, int y) computed the span offset as y * info.Height + x, which is wrong for row-major pixel layout. The correct formula is y * info.Width + x.

      On non-square pixmaps this produced completely wrong offsets — e.g. requesting pixel (3, 2) on a 10×5 image gave offset 13 instead of 23, pointing to the wrong row entirely.       The existing tests all used 3×3 (square) pixmaps, masking the defect. Fix the formula in the implementation and in the test assertions, and add two new tests using non-square pixmaps (10×5 and 8×3) that verify both span length and pixel identity across all positions.

      Rework the lifecycle of singleton instances (#4080)

      Fixes: https://github.com/mono/SkiaSharp/issues/3817

      SKFontManager.Default (and every other process-global singleton) threw on first access in 4.147.0-preview.1.1:

      System.TypeInitializationException: ... 'SkiaSharp.SKObject' ...
 ---> 'SkiaSharp.SKTypeface' ---> System.NullReferenceException
   at SkiaSharp.SKTypeface..cctor()
   at SkiaSharp.SKTypeface.EnsureStaticInstanceAreInitialized()
   at SkiaSharp.SKObject..cctor()

      The crash was a type-initializer (static constructor) cycle. SKObject..cctor eagerly called SKColorSpace/SKData/SKFontManager/SKTypeface/SKBlender/ SKColorFilter.EnsureStaticInstanceAreInitialized(). SKTypeface..cctor in turn reads SKFontManager.Default and SKFontStyle.Normal, which re-enter SKObject on the same thread. The CLR returns the half-built SKObject/SKTypeface type with null fields instead of blocking, producing the NullReferenceException — and because a failed cctor is cached for the process lifetime, the types stay permanently poisoned.

      While fixing the cycle we found two more lifecycle hazards in the same code paths that caused intermittent native crashes (notably an AccessViolation / STATUS_HEAP_CORRUPTION on net48/x86 under GC pressure). All three are fixed here.

      ~~ Break the static-init cycle ~~

      Delete the eager SKObject..cctor singleton chaining. Each singleton is now created lazily and per-type via LazyInitializer.EnsureInitialized on first access (CreateSrgb, SKData.Empty, SKFontManager.Default, SKTypeface.Default, the gamma color filters, the blend-mode blenders, the preset font styles). No wrapper type's initialization touches another wrapper type, so the static-initializer graph is acyclic and the #3817 re-entrancy cannot recur.

      ~~ Stop teardown from freeing shared native singletons ~~

      The singleton wrappers previously owned their native handle (owns: true). On teardown the finalizer / DisposeInternal drove the shared immortal Skia static's refcount to zero, calling the C++ destructor — which free()d static (non-heap) storage and corrupted the heap (STATUS_HEAP_CORRUPTION 0xC0000374, surfacing as a random AccessViolation in whatever allocated next). Guarding only the public Dispose() was not enough, because DisposeInternal and the finalizer bypass that guard. The singletons are now wrapped dispose-protected with owns: false / unrefExisting: false, so the wrapper never owns the handle and there is nothing to free on ANY path (public dispose, DisposeInternal, or finalizer). The process-global native object lives for the process lifetime.

      ~~ Hold wrappers alive across P/Invoke ~~

      A native wrapper passed to (or used by) a native call could be collected and finalized mid-call when nothing else rooted it — e.g. SKPathMeasure(path) reads path.Handle, then a concurrent GC finalizes path and frees the SkPath while sk_pathmeasure_new_with_path is still reading it. Add GC.KeepAlive for both this and native-wrapper arguments across the P/Invoke boundary in SkiaSharp, HarfBuzzSharp, Skottie, SceneGraph, and Resources, closing the in-flight use-after-free window (worst on net48 Release under GC churn).

      ~~ Tests ~~

      Add focused regression and concurrency coverage:

      • SKSingletonInitTest / SKSingletonConcurrencyTest — cycle-free init and races across the singleton getters.
      • SKHandleDictionary{Reentrancy,Reservation,StaleWrapper,DisposeProtected} tests — the dispose-protected / one-wrapper-per-handle invariants.
      • SKManagedStreamConcurrencyTest — managed-stream callback concurrency.
      • Pr4080UseAfterFreeTest — a GC-hammer repro for the in-flight use-after-free, isolated into a serialized collection.
      • A standalone SkiaSharp.Tests.SingletonInit.Console project that asserts pure-process, first-touch singleton init in isolation.

      API and behavioral changes: none.

      Fixes: https://github.com/mono/SkiaSharp/issues/2550 Fixes: https://github.com/mono/SkiaSharp/issues/2445

## Breaking changes

### Default font and typeface behavior

**Compatibility:** Behavioral

**Release-note blurb:** Default-constructed fonts now use an empty typeface,
while paint and missing-family fallbacks return explicit default typefaces.

**Affected APIs:** `SKFont`, `SKPaint.Typeface`, `SKPaint.Reset`,
`SKTypeface.FromFamilyName`, `SKTypeface.Default`

#### Previous behavior

- `new SKFont()` stored a null typeface and resolved the platform default when
  measuring or drawing.
- `new SKPaint().Typeface` and `SKPaint.Reset()` exposed null.
- On Android, `SKTypeface.FromFamilyName("missing")` could return null.

#### New behavior

- `new SKFont()` and assigning a null `SKFont.Typeface` produce
  `SKTypeface.Empty`; text measures to zero and does not draw.
- New or reset `SKPaint` instances expose `SKTypeface.Default`.
- Missing Android family names fall back to `SKTypeface.Default`.
- Default resolution uses the managed font manager, avoiding the Android API 36
  startup crash tracked by [#3693](https://github.com/mono/SkiaSharp/issues/3693).

#### Reason

Skia m132 removed lazy default-typeface resolution. SkiaSharp moved default
font lookup into the managed layer
([#3730](https://github.com/mono/SkiaSharp/pull/3730)).

#### Recommended action

Pass the desired typeface explicitly and use the font manager for strict
family matching:

```csharp
var font = new SKFont(SKTypeface.Default);
var missing = SKFontManager.Default.MatchFamily("MissingFont");

Use Typeface.IsEmpty rather than a null check when detecting an empty font.

SKStream.Move(long) rejects out-of-range offsets

Compatibility: Behavioral

Release-note blurb: SKStream.Move(long) is obsolete and throws for values that do not fit the native 32-bit offset instead of silently truncating them.

Affected APIs: SKStream.Move(long)

Previous behavior

Offsets outside the 32-bit range were truncated by an unchecked cast.

New behavior

Out-of-range offsets throw OverflowException, and the overload produces an obsolete warning (#3740).

Reason

The native stream API accepts a 32-bit offset; silent truncation could seek to the wrong position.

Recommended action

Validate the range and call Move(int).

Ganesh Vulkan requires Vulkan 1.1

Compatibility: Behavioral

Release-note blurb: Ganesh Vulkan now requires Vulkan 1.1; attempting to create a context for Vulkan 1.0 aborts the process instead of returning null.

Affected APIs: GRContext.CreateVulkan, GRVkBackendContext.MaxAPIVersion

Previous behavior

Unsupported Vulkan versions returned a null context, allowing a raster fallback.

New behavior

Upstream commits 0a3150b03b and dfea59a30f require Vulkan 1.1 and make the minimum-version check fatal (#4600).

Reason

Ganesh now acquires Vulkan 1.1 core entry points unconditionally.

Recommended action

Create the instance as Vulkan 1.1 or later and set the backend context to the same version:

const uint Vulkan11 = (1u << 22) | (1u << 12);
appInfo.ApiVersion = Vulkan11;
backendContext.MaxAPIVersion = Vulkan11;

Choose another backend before context creation on Vulkan 1.0-only hardware.

Vulkan backend context fields removed

Compatibility: Source and binary

Release-note blurb: GRVkBackendContextNative removes five legacy fields; custom Vulkan interop must use the typed extension and feature objects and manage instance/device ownership itself.

Affected APIs: GRVkBackendContextNative

Previous behavior

The struct exposed fMinAPIVersion, fInstanceVersion, fExtensions, fFeatures, and fOwnsInstanceAndDevice.

New behavior

Those fields are removed (#3741).

Reason

Skia replaced the legacy fields with typed Vulkan extension and feature objects and stopped owning the instance/device through the backend context.

Recommended action

Delete assignments to removed fields, use fVkExtensions and fDeviceFeatures or fDeviceFeatures2, and manage Vulkan object ownership outside the context.

Vulkan YCbCr conversion layout changed

Compatibility: Source and binary

Release-note blurb: Vulkan YCbCr conversion info gains a Components field, changing its native layout; the managed type is also renamed to GRVkYcbcrConversionInfo.

Affected APIs: GrVkYcbcrConversionInfo, GRVkYcbcrConversionInfo, GRVkYcbcrComponents, GRVkImageInfo.YcbcrConversionInfo

Previous behavior

The conversion info lacked component mapping and used the inconsistent Gr prefix.

New behavior

The layout includes Components; the generated type uses the GR prefix and the compatibility type loses its former value-equality members (#4001, #3741).

Reason

Upstream Skia added Vulkan component mapping and replaced its legacy YCbCr conversion structure.

Recommended action

Update type names, initializers, equality code, and any native layout assumptions. The managed rename and removed equality members also appear in the generated breaking API diff.
